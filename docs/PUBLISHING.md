# 发布工作流

发布管理页把内容保存后的 Git、同步、校验和 Mizuki 构建串成一条可检查的本机流程。所有写操作都需要用户在页面中明确触发。

## 发布顺序

### 本地内容模式

1. 运行发布前检查与发布校验。
2. 勾选受管理内容文件并检查逐文件差异。
3. 编辑 Conventional Commit 说明，提交所选文件。
4. 在已配置上游分支时推送当前分支。
5. 运行 Mizuki 真实构建并检查日志。

### 独立内容仓库模式

1. 发布校验先使用安全同步协议更新 Mizuki 工作副本，再运行 `pnpm check` 与 `pnpm type-check`。
2. 在独立内容仓库中提交选中的源文件并推送其当前分支。
3. 当受管理内容没有未提交变更时，显式运行独立内容同步。
4. 面板只允许为刚同步的内容提交运行 Mizuki 构建。

独立模式的提交与推送目标始终是内容仓库。同步和构建在 Mizuki 根目录运行，面板不会把同步产生的工作副本加入内容提交。

## 发布前检查

面板每次刷新都会重新读取 Git，不缓存文件状态。检查项包括：

- 当前内容来源可写，且目标目录本身是 Git 仓库根目录。
- 当前位于命名分支，没有未解决的合并冲突。
- 暂存区没有用户预先暂存的内容。
- 待选文件位于文章、特色页数据、媒体、追番内容或站点配置等已登记目录中。
- 无关文件单独显示并禁用选择，不会进入面板创建的提交。
- 推送前存在上游分支，并显示当前分支相对上游的领先、落后数量。

遇到游离 HEAD、冲突或已有暂存项时，提交入口会关闭。面板不会自动解决冲突、取消用户暂存或设置远程地址。

## 选择性提交与差异

文件列表来自 `git status --porcelain -z`，支持新增、修改、删除和重命名。提交前可以查看每个受管理文件的文本差异；二进制或过大的新文件只显示摘要。

面板使用字面量 Git 路径参数，只暂存当前勾选项，并在提交前再次核对实际暂存文件。仓库已有暂存内容会阻止操作。表单将类型、作用域和本次说明组合为 Conventional Commit，并展示完整提交预览，例如：

```text
feat(content): publish blog updates
docs(posts): update installation article
fix(config): correct navigation link
```

## 推送、凭据与失败处理

推送执行当前分支已有的上游配置，不接受页面输入的任意远程地址，不使用 force push，也不会自动 pull。Git 凭据继续由本机 Git Credential Manager、SSH Agent 或用户已有配置负责；面板不读取或保存凭据。

失败时遵循以下规则：

- 提交失败会取消本次选择产生的暂存状态，不改动工作树文件。
- 安全同步由 Mizuki 同步协议负责事务恢复；同步失败时不能进入构建。
- 校验或构建失败只保留日志，不回滚用户已经保存的源内容。
- 本次面板会话创建且仍位于 `HEAD` 的提交可以显式还原。还原使用新的 `git revert` 提交，不改写历史；已提交文件再次变化时会拒绝自动还原。

## 构建日志

校验、同步和构建一次只运行一个任务。页面轮询任务状态并默认保留最近 500 行去除 ANSI 控制符后的日志；保留条数、字号和自动滚动可在设置中调整。发布表单默认不记忆，开启后只在提交成功时记住类型/作用域，提交说明和勾选文件不保存。详见 [设置阶段 6](PANEL_SETTINGS_STAGE_6.md)。日志示例：

- 发布校验：`pnpm check`、`pnpm type-check`；独立模式会先运行 `pnpm sync-content`。
- 独立同步：`pnpm sync-content`。
- 正式构建：`pnpm build`。

这些命令都在连接的 Mizuki 根目录中执行，使用 Mizuki 自己的 Astro、MDX、配置和内容加载管线。
